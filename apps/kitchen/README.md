# Madar Kitchen (مطبخ مدار)

The kitchen display, in React Native (Expo, TypeScript) on the shared Rust
core, to [`docs/specs/kitchen-target-spec.md`](../../docs/specs/kitchen-target-spec.md).

```
apps/kitchen (React Native)
  └─ modules/madar-kitchen-core      turbo module generated by uniffi-bindgen-react-native
       └─ rust-core/crates/madar-kitchen-ffi   thin uniffi facade, kitchen calls only
            └─ madar-core             session, sync feed, outbox, realtime, LAN
```

## Run

**Design / mock (web or simulator, no backend):**

```sh
npm install
npm run web            # http://localhost:8081 — always the mock
npm test               # board rules + en/ar key parity (node --test)
npm run typecheck
```

Mock sign-in: any manager email/password; staff PINs `111111`, `222222`
(cooks) and `999999` (manager), any name. Settings → *Mock tools* fakes the
network and sends test orders. `EXPO_PUBLIC_MOCK=1` forces the mock on a device.

**Real (iPad / Android, the Rust core):**

```sh
# 1. build the Rust binding (once, and after any change to madar-kitchen-ffi)
npm run core:ios -- --sim-only        # drop --sim-only for a device build
ANDROID_NDK_HOME=~/Library/Android/sdk/ndk/28.2.13676358 npm run core:android

# 2. run (prod API by default; point at a local backend for testing)
EXPO_PUBLIC_MADAR_API=http://localhost:8082 EXPO_PUBLIC_MADAR_ENV=dev \
  npx expo run:ios --port 8083
```

Use a Metro port other than 8082, which is the local backend's.

**A local kitchen to test against:** with MadarRust running on `:8082`,
`python3 scripts/dev-kitchen-demo.py` gives the local demo org three
sections, a menu routed to them, a kitchen cook, and fires four rounds;
`--fire` fires two more. Its header lists the sign-ins. Local only — it
refuses anything but localhost.

## Device flow

1. **Setup** (route `setup`): a manager signs in with their Madar email and binds the device to a branch (DV-1). The manager is signed out.
2. **Login** (`login`): a cook signs in with name + staff PIN (DV-2). The core needs this session to read the feed (DV-5).
3. **Sections** (`sections`, first sign-in only): one or more sections, or the expo (KB-1, EX-1). Kept in `kitchen-device.json` beside the core's store until `DeviceConfig` grows these fields.
4. **Board**: the core's local rows, re-read on every realtime `kitchen.*` event and every 3 s. A bump goes outbox first (offline-safe), records who did it (DV-3), and the board re-reads.

The route comes from `KitchenCore.state()`; the app never decides it.

## Layout (the dashboard's)

```
src/
  app.tsx              root: fonts, language, route → screen, the board poll
  data/backend.ts      the one interface; native-backend.ts (core) · mock-backend.ts
  data/store.ts        Zustand: last read of the backend + screen state
  features/<name>/     board · expo · setup · auth · settings
  components/ui/       primitives: Txt, Button (+ Segmented), Sheet, Field
  components/app/      composed: StatusPill, EmptyState, SectionHeader, TopBar, banners
  theme/tokens.ts      system v2 tokens — same values as MadarDashboard globals.css
  i18n/locales/        en.json, ar.json — every string through t()
```

## Gaps (from wiring against the real feed)

The kitchen feed (`KdsTicketView`) doesn't carry these yet, so the screens
show what's there. Each needs a server + madar-shared change (gated by an
authz capability):

- the waiter and the order note (OF-2), voided lines (OF-5), online orders (OF-6)
- the time a part was bumped, so recall can be limited to 10 minutes (KB-4)
- the expo hand-off (EX-4): today it is device-local
- several sections or expo on one device in the core's `DeviceConfig` (KB-1)
- whole-part bump as one call (today: one outbox op per line)
- LAN-only state for the banner (LN-*): a device shows online or offline
- the chime (KB-5): the core's ping reaches the app; no sound asset yet
