# Setup / QR codes (`/settings/qr`): differences from the web

One line per difference: what the web does, what Flutter does, why. Rows marked "question" port
the web's behaviour as it is and ask the owner whether it is intended.

| Row | Web | Flutter | Why |
|---|---|---|---|
| SET-QR-027 branch switch | Results and inline errors are kept per card, not per scope: after switching the header branch, a branch card still shows the PREVIOUS branch's code (with nothing saying so), ready to download and print. | A branch card's code and error are dropped when the header branch changes (org cards' codes stay, they are still the org's; every card's go when the org changes). A code that lands after the scope moved is not shown. The in-mall typed fields stay, as on the web. | A code for the wrong branch, printed and stuck on a door, is a web bug; the web's own table sheet drops on a branch switch for exactly this reason (SET-QR-024). Pinned by `qr_page_test` "SET-QR-027 (divergence)…". |
| SET-QR-028 failed tables read | A failed `GET /branches/{id}/tables` shows "This branch has no tables yet. Add them on the floor plan first." — no error, no retry. | The card shows the load-failed state ("Couldn't load this" + the server's words + Retry, refetching only the tables). | A failure that reads as "nothing here" is a web bug (SPEC 6.3). Pinned by `table_codes_test` "SET-QR-028 (divergence)…". |
| SET-QR-012 over-length | zod's default message, in English in both languages ("Too big: expected string to have <=80 characters"). | The web's own `common.atMostChars` ("At most 80 characters" / "80 حرفًا على الأكثر"). | English inside the Arabic UI is a web bug. Pinned by `qr_page_test` "SET-QR-012…". |
| SET-QR-008 – 013, 021 caching | Each press calls the endpoint (no React Query). | Each code is a read keyed by its exact params, warmed on intent (owner rule), so a press answers from that warm read; the press then drops the read, so every press asks the server again. | The server redraws the card from the org's current brand on every request (MadarRust qr_card/handlers.rs:728-729); the cache only bridges hover to press. Pinned by `qr_intent_test` and `qr_page_test` SET-QR-013. |
| SET-QR-023 print | "Print sheet" calls `window.print()`; print CSS hides the chrome, gives tiles a dashed border on white and never splits one across pages. | "Print sheet" builds an A4 PDF of the sheet (three tiles a row, dashed cut lines, white, the label large, a row never split across pages) and opens the system print dialog (`printing`). | No browser print in a Flutter app; the PDF reproduces the print stylesheet. Pinned by `table_codes_test` "SET-QR-023…". |
| SET-QR-015/018 narrow result | Beside the form (from 1024) the 256-px result card keeps Copy link and Download side by side. | They stack in that 256-px card as they do on a phone. | Side by side, "Download" was cut short at the app's type size. |
| SET-QR-013 spinner | The busy card's Generate shows a spinning RefreshCw icon. | The kit button's spinner (`DashButton.loading`), which honours reduced motion. | Kit control. |

| SET-QR-012 in-mall warming (question) | No warming: one call per press. | The in-mall Generate is never warmed; the org and branch cards are. | The QR GETs are get-or-create (MadarRust qr_card/db.rs:34-73): warming the in-mall card would create a permanent Shlink link per typed place/floor/unit. Owner question: should these GETs have no side effects (create only on an explicit press), so every card can be warmed? |
| SET-QR-021 run outlives the branch | A "Make codes" run that finishes after the header branch changed still sets its codes (table-codes.tsx:69). | The late answer is dropped; the new branch shows its own "Make N codes". | A sheet for the wrong branch would be printed and stuck on the wrong tables. |
