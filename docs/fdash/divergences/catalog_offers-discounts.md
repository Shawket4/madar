# Catalog offers / Discounts (`/discounts`): differences from the web

One line per difference: what the web does, what Flutter does, why. Rows marked "question" port
the web's behaviour as it is and ask the owner whether it is intended.

| Row | Web | Flutter | Why |
|---|---|---|---|
| OFFR-DSC-016 confirm name | The delete confirm reads `Delete "<raw English name>"?` in both languages. | The confirm names the discount as the table does: its Arabic name in the Arabic UI, the English one otherwise. | English inside the Arabic UI is a web bug (SPEC 6.3). Pinned by `discounts_page_test` "OFFR-DSC-016 (divergence)…". |
| OFFR-DSC-030, 044 step check | `<input type="number" step="0.5" min="0" max="100">` with no `noValidate`: the browser's own bubble stops a value off the 0.5 step, below 0 or above 100 before the form rules run. | No native bubble: the form's own check refuses below 0 (`discounts.valueNegative`), a percentage above 100 (`discounts.percentRange`) and a value off the 0.5 step with a new line, `discounts.valueStep` "Enter a value in steps of 0.5 (for example 12 or 12.5)." (this unit's supplement, with Arabic), under the field and before any request. A stored 12.25 % opens as it is and cannot be saved until moved to a 0.5 step, as on the web. | Platform (no browser validation). The wording of the step line is new: the web has no key for it (inventory: orchestrator decision). |
| OFFR-DSC-041 Esc / clear / trim | `<input type="search">`: the browser's own × and Esc empty it; the typed text filters untrimmed (`"meal "` finds nothing). | The kit's search box shows its clear × while it has text; Esc in the box empties it (after an open popover closes); the query is trimmed (`"meal "` finds Staff Meal). | Platform; trimming is the kit's (kit batch 2, item 16). |
| OFFR-DSC-009 question: search with no match | A search that matches nothing shows the page's empty state "No discounts yet / Create your first discount…" (the DataTable is given one empty state). | Ported as is. | Product quirk, not plainly a bug; owner question whether a "No results found" is wanted. |
| OFFR-DSC-026 question: Arabic label | `bilingualField.arabicLabel` in ar.json is "{{label}} (إنجليزي)" ("(English)") on the ARABIC name box. | Ported as is (the shared web key, used by every bilingual form). | Copy defect in the web's shared ar.json; changing it would change every page's bilingual field. Owner/orchestrator question. |
| OFFR-DSC-028 question: "(EGP)" | `discounts.amountValue` hard-codes "(EGP)" whatever the org currency. | Ported as is. | The web's words; every org is EGP today. |
| OFFR-DSC-034 question: Arabic name on rename | The dialog sends `name` and `name_translations` together; the backend's PATCH keeps the stored translations whenever `name` is present (only `en` follows the name), so an edited Arabic name is dropped by the server. A cleared Arabic box sends nothing, so it is never cleared either. | Same request as the web; the mock answers as the backend does (`discounts_mock_test` "OFFR-DSC-034 PATCH…"). | Backend behaviour (MadarRust `discounts/handlers.rs`, `ensure_translations_json` instead of `merge_translations_json`); reported, not changed here. |
| OFFR-ALL-004 question: server sentences in Arabic | `getErrorMessage` shows an uncoded server sentence (kind prefix stripped) in English in the Arabic UI ("Discount not found", "value must be >= 0"). | Same words; in real mode the core words refusals in the active language and they pass through. | Kept to the web's rule; mock mode shows the backend's English. |
| OFFR-DSC-026, 028 box direction | The English name box and the value box take the page's direction (`bilingual-field.tsx:30`): in the Arabic UI they are right to left, so a Latin name or a figure starts at the right edge. | The English name box and the value box are always left to right (the Arabic box always right to left), whatever the UI language. | A Latin name or a number typed right to left reorders punctuation and signs; the box follows the text it holds. |
| OFFR-DSC-023 dropped row | When the open discount leaves the list (deleted elsewhere, a refetch), the dialog unmounts without `onOpenChange`, so `?edit=<id>` stays in the address (`discounts-page.tsx:169`). | The dialog closes and `?edit` is removed, as for any other close. | A stale `?edit` in the address reopens nothing and misleads a shared link; every other close already removes it. |
