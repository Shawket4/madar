# Catalog menu / pricing (`/menu/pricing`): differences from the web

One line per difference: what the web does, what Flutter does, why. Rows marked "question" port
the web's behaviour as it is and ask the owner.

| Row | Web | Flutter | Why |
|---|---|---|---|
| MENU-PRC-028 add-on edits on another page | Save collects add-on cells from the CURRENT add-on page only: a cell staged on page 2 is counted in "N unsaved changes", not written, and then dropped by the "all saved" reset. | Every add-on shown so far is remembered; its staged cells are written whatever page shows. | A staged edit the bar counts and Save silently throws away is a lost save (SPEC 6.3). Pinned by "MENU-PRC-028 (divergence) an add-on staged on another page is still saved". |
| MENU-PRC-029 showing a channel the branch hides | "Show at this scope" on a channel whose branch hides the target stages a change, Save plans no write (`available → is_available: null`), toasts "Saved 1 changes" and the cell is hidden again after the refresh; with a typed price the PUT also carries `null` and the hide stays. | When the cell's inherited availability is hidden (the branch hides it) and the person shows it, the PUT carries `is_available: true` (the backend resolves channel → branch per field, `menu_unification_expand.sql` §6); "Remove override" stages the inherited availability, so clearing never turns into "show here". Every other case writes exactly what the web writes. | A Save that says "saved" and writes nothing is the worst outcome a form can have (SPEC 6.1). Pinned by "MENU-PRC-029 (divergence) …" (driven) and the `planCell` unit tests. |
| MENU-PRC-030 search from page 2+ | A new search keeps the page number, so searching from page 2 can ask for an empty page: "No menu items" shows with the pager hidden; the only way back is clearing the search. | A new search (either tab) starts at page 1. | An empty result for a search that has matches is a defect, not a product choice. Pinned by "MENU-PRC-030 (divergence) a new search starts at page 1". |
| MENU-PRC-031 invalid-price toast name | The name is looked up on the CURRENT items page only: a bad price on an item expanded on another page reads "Enter a valid price for " with no name. | The name is kept with the item's staged sizes, so the toast names it wherever it is. | An empty name in an error is a defect. Pinned by "MENU-PRC-031 (divergence) …". |
| MENU-PRC-032 channel add-on reads | The four `/delivery/channel-addon-overrides` reads have no loading or error state: while pending or after a failure their cells show as inherited and edits are planned as if no channel row existed. | They gate the add-ons tab with the add-on list and the branch rows: skeleton while any loads, the error state (server words + Retry, which asks all six again) when any fails. | Showing "inherited" for a price that is really overridden misleads the person editing it. Pinned by "MENU-PRC-032 (divergence) …". |
| MENU-PRC-033 one-price items | A simple item's single size shows its stored label "one_size" (also in Arabic). | It reads `recipes.oneSize` ("One size" / "حجم واحد"), as the recipe builder and the bases page name it. Inactive sizes are still listed and editable, as on the web. | A raw sentinel shown to people is a web bug. Pinned by "MENU-PRC-033 … reads "One size"". |
| MENU-PRC-027 why a save failed | "Saved {{ok}}, {{failed}} failed" only; the server's reason is collected and never shown (a refused person reads "Saved 0, 3 failed"). | Same title, with the first failure's server words as the toast's description. | SPEC 6.1: a failed mutation toasts the server's words. Pinned by "MENU-PRC-027 some failed …" and "MENU-AREA-008 … Save refused with the server's words". |
| Prefetch (`/menu/overrides`) | `prefetchRoute` has a case only for the retired `/menu/overrides` (a redirect no nav row points at), warming the old page's keys (`sort: "overridden"`, `branch_id`, categories); hovering "Pricing & Availability" warms nothing. | The `/menu/pricing` route warms what the merged page reads on mount with a branch scoped: catalog page 1, add-on page 1, the branch add-on rows and the four channel reads. | The case's intent (warm the overrides screen on hover) aimed at the screen it became; the old keys would only cost requests. Pinned by "prefetch: pointing at the sidebar row …". |
| MENU-PRC-022 phone breakpoint | `useIsMobile()` switches to cards below 768 px. | Below 760 px (the app-wide `DashBreakpoints.phone`). | Kit breakpoint; 8 px apart. |
| MENU-PRC-016/017 hit targets | The switch is 24 px (36 px on phone rows), the × 20 px. | The switch keeps its 28 / 36 px face inside a 44 px target (SPEC 2: targets ≥ 44); the × is the kit's 24 px clear button. Desktop cells are therefore taller than the web's. | Accessibility rule. |
| Backend read/write split (question) | — | The mock serves `/branch-addon-overrides` and `/delivery/channel-addon-overrides` from the unified `menu_price_overrides` table the page writes, as the backend does AFTER `deploy/menu_unification_shim.sql` turns them into views. | Question for the owner: on a backend where the shim is not applied, those two reads still come from the legacy tables, so add-on prices and hides saved on this page (and on the web) would not show after the refresh. |
